# demo-it Mind Map

[1] **Project Architecture Overview** - Entry point for the transcript-driven demo system, linking the control surface [2], canonical execution model [3], transport contract [4], and development workflow [5].
[2] **Client Control Surface (CLI + Neovim Plugin)** - `demo-it` CLI and local Neovim commands act as thin clients that forward user intent over the daemon protocol [4], while CLI workspace tmux bootstrap mode (`start [path]` or direct `<path>` -> `<name>-demo`/`<name>-notes`) defaults to current working directory for `start`, kills previously managed demo-it sessions for single-workspace flow, accepts workspace directories (`<workspace>/demo-it.md`) or transcript file paths directly, and can replay `demo-it` block actions (`insert-text`, `key`, `key-macro`, `open-slide`, `killall-pane`, `kill-pane`, `split-pane`, `split-pane-vertical`) plus step-level `slide` shorthand and optional step-level `auto_slide_in_ms` timers from `demo-it.md` with pane-safe behavior (`split-pane` keeps presenter focus, action inputs can optionally target pane selectors like `active`/`last`/index, slide changes target a Neovim pane via `slide`/`open-slide`/`key`+`slide` with auto-start, `kill-pane` closes the latest pane by index, `killall-pane` keeps only the initial pane by index, and auto-advance scheduling uses guarded delayed `next` so manual navigation cancels pending timers), adds isolated tmux authoring capture via `record` (`<workspace>-record` session) that maps tmux pane hooks (`after-split-window`, `after-kill-pane`) plus shell input logging into generated `demo-it` markdown actions (`split-pane`/`kill-pane` + grouped `key-macro` sequences split on `Enter` with a 500ms start delay and best-effort per-event `delay_ms`) and prompts for Enter before tmux handoff (override with `--yes`), then ends on recording shell exit while emitting to stdout (compatible with shell redirection) or directly to `-f <file.md>`, refresh speaker notes in the notes session as `next`/`prev` move through the latest workspace using in-memory daemon notes plus scratch Neovim buffers (no workspace notes file writes), expose workspace-step metadata in `next`/`prev`/`rerun` responses, report `DemoItNext`/`DemoItPrev`/`DemoItRerun` progress in-command-line as slide/step confirmation instead of popup dialogs, default `:DemoItStart` workspace bootstrap to Neovim's current working directory when no path is provided, enable builtin presentation mode by default on start (`DemoItPresentationEnable`) with zen-like low-noise window options, markdown rendered/raw conceal switching, and markdown-diagnostic suppression while active, light viewport padding, configurable font sizing (`presentation.font.neovide_scale` + `presentation.font.kitty_delta`) with Kitty bump/revert support, tmux demo-session `status off` defaults, and session navigation key table shortcuts (`C-s` then `n`/`p` -> `demo-it next`/`prev`) that call the CLI directly, expose preview wrappers (`DemoItPreview`, `DemoItPreviewStop`) that prefer `LivePreview` and fall back to `MarkdownPreview`, and expose lifecycle helpers (`status`, `run-status`, `notes`, `show`, `record`, `kill`) for the managed tmux session in [5], all within the architecture map [1] and canonical state model [3].
[3] **Canonical Run State and Transition Engine** - `internal/session` owns run status, cursor/history transitions, and idempotent execution ledger semantics consumed by the daemon service via [4], exposed through the client surface [2], and anchored in the architecture index [1] and quality loop [5].
[4] **Daemon Service and Wire Protocol** - `demo-itd` + `internal/daemon` implement Unix-socket NDJSON request/response handling with validated command envelopes from `internal/protocol`, mediating between user-facing controls [2] and canonical state transitions [3]; request envelopes are minimal (`id`, `cmd`, `run_id`, `args`) without unused `client_id`, while state responses stay intentionally small (`run_id`, `status`, `current_slide`, `capabilities`, `speaker_notes`, transition metadata) and keep cursor-interaction/default-focus internals private; capability metadata now advertises action support (`set_auto_next`, `set_notes`, `split_panes`, `kill_panes`, `key_macro`) for CLI/daemon compatibility checks, daemon-owned auto-advance scheduling is exposed via `set_auto_next` (one-shot timer per run that triggers delayed `next` using CLI/socket/env context), daemon notes state is updated via `set_notes`, and transcript parsing enforces unique `demo-it` block titles for deterministic step identity, all within architecture [1] and workflow [5].
[5] **Development Environment, Docs, and Verification** - Nix/devenv bootstrap, flake-packaged CLI/daemon outputs plus a shared Neovim plugin package (`packages.<system>.demo-it-nvim`) for nixvim consumers across Linux and Darwin systems, Home Manager module support for running `demo-itd` as a persistent user service with shared socket environment (including documented flake wiring via `inputs.demo-it.homeManagerModules.default` and `services.demo-it.enable`), direnv integration, trusted project-local Neovim bootstrap (`.nvim.lua` + `exrc`), protocol/plan documentation (including `record` authoring semantics for key-macro delays and grouping), CLI action debug logging via `DEMO_IT_DEBUG_LOG`, pane-level trace capture via `trace-next` (`tmux pipe-pane` raw logs plus normalized textual snapshots in workspace `.demo-it/traces`), targeted tmux e2e snapshot coverage consolidated under `test/e2e` for trace flow/recording/pane behaviors, `auto_slide_in_ms` timer chaining, and slide/notes synchronization via isolated test-server wrappers (`tests-e2e`), baseline unit coverage for daemon entrypoint startup/shutdown (`cmd/demo-itd`) and unix-socket transport client behavior (`internal/client`), local binding path override via `DEMO_IT_PATH` with `start` syncing tmux runtime env (`DEMO_IT_PATH`/`DEMO_IT_RUN_ID`/`DEMO_IT_SOCKET`), devenv-local daemon socket defaults (`$DEVENV_ROOT/.devenv/demo-itd.sock`) with strict local-daemon guard (`DEMO_IT_REQUIRE_LOCAL_DAEMON=1` -> clear `devenv up` hint when unavailable), workspace assets (`demo-it.md` with optional `slides/*`) and example coverage for both slide-first and shell-only demos, and test boundaries provide the iteration framework that keeps control paths [2], runtime state logic [3], and daemon transport [4] coherent within the project overview [1].
